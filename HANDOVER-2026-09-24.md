## 1. Bookings (P2-01)

### Which sheets

Sheet 07 is the main one, but bookings span **four provider kinds across Sheets 07–13**:

| Sheet | Kind | Booking surface |
|---|---|---|
| **07** | Care facility (hospital + clinic) | **Bookings tab**: Day/Week timeline, week strip, current-time line, "Block time" FAB. **Booking request sheet**: Accept / Decline / Suggest another time. Plus "Contact requests" — a pre-bookings fallback screen listing call/WhatsApp/directions taps. |
| 08 | Hospital | **Services & prices** — the bookable catalogue: name, duration, price, "Bookable" switch, NHIS toggle, available days, "what to bring". This is what a booking is *of*. |
| 09 | Clinic | Jobs and Reviews. No booking surface, but confirms the clinic tab bar has Bookings. |
| **10** | Practitioner | **Schedule (agenda)** with consult types — clinic / video / home visit. **Availability**: per-day time ranges, consult-type chips, home-visit radius, break between appointments. **Appointment detail** → "Start video call". |
| 11 | Practitioner | **Services & fees** — video / clinic / home visit, each with duration + price + a switch. Same shape as Sheet 08's services. |
| **12** | Trainer | **Schedule** with 1-on-1, group ("14/20 spots") and online sessions. **Session detail**: capacity, price per person, attendee list, QR check-in. |
| 13 | Trainer | Programmes, challenges, events, groups. Sessions come from here. |

### What this tells you about the data model

Read across those sheets and one model falls out:

- **A bookable thing** = a service with `name, duration_minutes, price, is_bookable`, plus per-kind extras (NHIS flag and "what to bring" for facilities; consult mode for practitioners; capacity and per-person price for trainers). `provider_catalogue_items` **already has `item_type`, `duration_minutes`, `price` and `capability_required`** — the plan's P2-01 line says services link to catalogue items with `item_type in (service, session, package)`. Use it; do not build a parallel services table.
- **Availability** is per-provider (and for practitioners, per consult-type): day-of-week ranges, a break interval, and a home-visit radius.
- **A booking** needs: provider, department (hospitals have departments now — P1-08), service, patient, start/end, status (`requested → confirmed → completed | declined | cancelled | no_show`), a patient note, and for groups a capacity count.
- **Group sessions** (trainer) are a booking with many attendees — capacity, attendee list, check-in state. Decide early whether that is the same table with a capacity column or a separate attendee join; Sheet 12 needs both "14 of 20 spots" and a per-attendee check-in toggle.

### What does not exist yet

**There are no booking tables at all.** The only match in the database is `period_preconception_appointments`, which is Plasence's and unrelated. Everything is greenfield.

### The gap nobody has flagged

**The patient side of booking is not designed anywhere.** Sheets 00–21 are the *provider portal* pack. There is no consumer mockup for browsing a provider's services, picking a slot, or managing a booking. The consumer app has no booking screens.

That matters because of the user's stated goal — finish the consumer side so the provider side does not force consumer rework. For bookings that is impossible today: **the consumer half has no design to build from.** Decide one of:

1. Commission consumer booking designs first, then build both sides together.
2. Build the DB + provider side, and ship a deliberately minimal consumer booking flow (service list → slot picker → confirm) without a bespoke design.
3. Defer bookings entirely and ship the vendor loop, which *is* complete.

**This is a product call, not an engineering one. Get it answered before writing any booking code.**

### Sequence when you do start

1. Availability + services on `provider_catalogue_items` (no new table).
2. `bookings` table + status transitions + RLS via `is_provider_member(..., 'bookings.manage', department_id)` — **the permission already exists and is already granted** to owner, admin, department_manager and staff.
3. Slot generation (availability minus existing bookings minus blocked time).
4. Provider screens, Sheet 07 first.
5. Consumer screens — blocked on the design decision above.
6. `dispatch_provider_alert(..., 'booking', ...)` already exists and routes to the Business app inbox; `use-push-router.ts` currently sends `booking` to Home because no screen existed. Point it at the new one.

## 2. Chat (P2-03)

### Reuse it. Do not rebuild it.

The consumer app has ~4,500 lines of working chat, and the tables are entirely generic:

- `conversations` — `type`, `is_group`, `group_type`, `last_message_at/preview/sender`, plus flagging and moderation columns
- `conversation_members` — `user_id`, `role`, `is_muted`, `is_archived`, `unread_count`
- `messages` — content, `message_type`, attachments, `reply_to_id`, edit/delete, moderation

Nothing in any of that is patient-specific. Existing functions: `get_conversations`, `is_conversation_member`, `fn_mark_conversation_read`, `fn_create_group_conversation`, `can_insert_conversation_member`, `user_can_manage_conversation`.

Consumer code to extract: `apps/consumer/hooks/chat/*` (`useConversationList`, `useDirectMessages`, `useGroupMembers`, `useCreateGroup`, `useJoinGroup`, `useSupportTicket`) and `apps/consumer/components/chats/*`.

### What is actually missing — four things

1. **No one-to-one conversation function.** Everything that exists is group-shaped. PLAN.md refers to `fn_get_or_create_direct_conversation`; it is documented but was **never written**.
2. **`conversations.enquiry_id` does not exist**, so a chat cannot be tied to the order it is about. Sheet 14 (Messages) assumes it can.
3. **No access rule.** P2-03 requires the patient to hold `full_access` premium and the provider the `paid_chat` privilege, enforced in chat RLS or `is_conversation_member`. `paid_chat` is listed in P1-07 as a `subscription_privilege` enum value **that has not been added yet**.
4. **Not in `packages/shared`.** P0-17 lists "Chat (conversation list, thread, composer, use-chat hooks)" as step 5 of the shared extraction. Nobody has done it. `packages/shared` currently holds only `theme/` and `supabase/`.

### Landmine

**`fn_create_group_conversation` exists TWICE** — two live overloads. This is the exact trap P0-15 documented: `CREATE OR REPLACE` does not replace a function when the parameter list changes shape, it creates a second one. Resolve which is authoritative and drop the other **before** building on it, or calls will fail ambiguously.

### Sequence

1. Drop the duplicate overload.
2. Extract chat into `packages/shared` (consumer smoke test after — it is the riskiest step, touching a shipped surface).
3. `fn_get_or_create_direct_conversation` + `conversations.enquiry_id`.
4. Add `paid_chat` to `subscription_privilege`; enforce both sides of the access rule.
5. Business app Messages tab (Sheet 14). Route `chat` in `use-push-router.ts` at it.

Budget this as an extraction plus three small DB additions. It is not a rebuild — PLAN.md reads like new work only because P2-03 lists the gaps rather than the reuse.

## 3. P1-01's three open bullets, and the category model

This is the piece the user has explicitly agreed to and wants planned properly.

### 3a. Current state

```
medication_enquiries.enquiry_type  CHECK (enquiry_type IN ('with_rx','otc','hcp_request'))
drugs                              has `category`, has NO prescription-only flag
provider_catalogue_items           has `category` (free text, 0 rows — no vocabulary established yet)
capabilities                       otc_medicines, rx_medicines, supplements, healthy_foods,
                                   medical_devices, herbal_products, wholesale, …
```

`trg_match_enquiry_to_vendors` (built this session) currently maps **only** `otc → otc_medicines` and `with_rx → rx_medicines`. Everything below extends that function.

### 3b. The model to build — two orthogonal columns, not one

Do **not** widen `enquiry_type`. It answers *"does this need a prescription?"*. Add a second column answering *"what kind of thing is it?"*. They are independent — a supplement is never `with_rx`.

```
medication_enquiries.enquiry_category text not null default 'medicines'
  check (enquiry_category in
    ('medicines','supplements','healthy_foods','medical_devices','herbal_products'))
```

Defaulted, so every existing row and every shipped client keeps working — this is the "additive parameter with a default" P1-01 asks for. `submit_medication_enquiry` takes it inside the existing `p jsonb` bag, so **the signature does not change** (same approach as `delivery_gps` this session).

**Category → capability, which is what routes the enquiry:**

| `enquiry_category` | `enquiry_type` | required capability |
|---|---|---|
| medicines | otc | `otc_medicines` |
| medicines | with_rx | `rx_medicines` |
| supplements | — | `supplements` |
| healthy_foods | — | `healthy_foods` |
| medical_devices | — | `medical_devices` |
| herbal_products | — | `herbal_products` |

A clean 1:1 with the existing `capabilities` table — no new vocabulary needed. This is what delivers the user's requirement: *medicine goes to pharmacists, nuts and seeds go to natural/wholefoods.*

**Rename nothing.** `medication_enquiries` keeps its name even though it now carries tiger nuts. Renaming a contracted table for tidiness would break the mobile contract for no functional gain; say so in a comment and move on.

### 3c. The dynamic consumer form — the user's main ask

`apps/consumer/app/(app)/(auth)/Medication/index.tsx` is hardcoded to medicine. Its state today:

```
name, drugId, dosage, quantity, unit('tablets'), urgency, rxPhoto,
areaMode, customArea, radius, notify, fulfilment, deliveryAddress
```

Category must drive **four** things, not just which fields show:

1. **Which fields appear.** `dosage` and the prescription upload are meaningless for tiger nuts. Devices want brand/model, not strength.
2. **The unit list.** `QUANTITY_UNITS` is currently tablets/capsules/bottles/vials/ampules/sachets/inhalers. Foods need kg/g/bags/bunches; devices need pieces/boxes.
3. **What the name field searches.** Medicines autocomplete against `drugs` via `search_drug_names`. **There is no equivalent for the other categories** — they should search `provider_catalogue_items`, which needs a search RPC that does not exist yet. Until it does, those categories are free-text entry, which is an acceptable first version.
4. **The copy.** "Find Medication", "Searching pharmacies", the pill iconography — all medicine-specific, in the form *and* in `ENQUIRY_STATUS_META`.

Suggested shape: a single `ENQUIRY_CATEGORIES` config in `hooks/use-medication-enquiry.ts` — one entry per category carrying `{key, label, icon, units[], fields[], searchSource, copy}` — and drive the form from it. One place to change when a category is added, and the Business app can import the same labels so both sides agree.

### 3d. The Business app also needs this

`apps/business/features/vendor/api.ts` `EnquiryRequest` and the Requests tab assume medicine: field is `medicationName`, the row icon is a `Pill`, the detail screen says "Prescription"/"OTC". Add `enquiryCategory` to the type and drive icon + label from it. `get_vendor_enquiry_inbox` must return the new column.

### 3e. The `rx_epharmacy` gate (bullet 2)

Half of this is already done. `trg_match_enquiry_to_vendors` **already** refuses to alert anyone for a `with_rx` enquiry while the flag is off — verified live this session. Still missing:

- `submit_medication_enquiry` should reject `with_rx` outright when the flag is off, rather than accepting an enquiry nobody will ever see. Read it with `is_feature_enabled('rx_epharmacy')` — that function exists (P0-07) and is allow-listed for this flag.
- When the flag is **on**, a `with_rx` enquiry must require `prescription_url`. Not enforced anywhere today.
- Consumer: hide the prescription path while the flag is off. `is_feature_enabled` is callable from the patient app.

### 3f. `drugs` prescription-only flag (bullet 3)

```
alter table public.drugs add column is_prescription_only boolean;   -- nullable: null = unknown
```

Nullable on purpose — a three-state answer (yes / no / nobody has checked) is honest, and a `not null default false` would assert every unreviewed drug is OTC, which is the dangerous direction to be wrong in.

Backfill from `drugs.category` and `atc_code` where it is unambiguous; leave the rest null. Then:

- The consumer picker shows "Prescription only" and disables OTC selection (Sheet 06 screen 4 already draws this for the vendor side).
- `submit_medication_enquiry` can force `enquiry_type = 'with_rx'` when the chosen `drug_id` is prescription-only, instead of trusting the client.
- **Treat null as "not confirmed OTC"** — do not silently let it through as OTC.

### 3g. Suggested order

1. Migration: `enquiry_category` + `drugs.is_prescription_only` + extend `trg_match_enquiry_to_vendors`'s capability map + extend `submit_medication_enquiry` (rx gate, prescription requirement, drug-flag enforcement) + `get_vendor_enquiry_inbox` returns the category.
2. Backfill script for `is_prescription_only`.
3. Consumer: the `ENQUIRY_CATEGORIES` config and the dynamic form.
4. Business: category on the Requests tab.
5. A catalogue search RPC so non-medicine categories get autocomplete.

Dry-run the whole loop end to end per category before calling it done — submit as `healthy_foods`, confirm only a `healthy_foods`-capable vendor is alerted.

**Working end to end, verified on prod:** the vendor loop. Submit (with GPS) → match trigger → vendor alert → inbox with real distance → quote → patient accepts → vendor order board → mark ready → patient sees pickup code → verify → completed.

**Done this session:** P0-16 security (PIN app lock, step-up, device management), P1-01 matching trigger, P1-02 quote fix, P1-03 Sheet 05 Orders UI, P1-05 reviews, P1-06 analytics, P1-08a–d staff accounts and departments, `provider_portal` gate.

**Bugs found and fixed — worth knowing because they suggest where to look next:**

- Vendor quoting had **never worked** (RLS subquery evaluated as a user who cannot see the row).
- The consumer review list was broken on **every** facility page (filtered on a non-existent column).
- Eight tables were unwritable on UPDATE (`updated_at` trigger, no `updated_at` column).
- Two review rules had never run (triggers attached to no table).
- `list_my_devices` was not app-scoped; `is_current` was hard-coded false.
- `get_provider_home` kept an `owner_id` guard past the P1-08b swap.

The pattern: **this database has a lot of code that was written, never called, and therefore never found to be broken.** When you pick up bookings or chat, assume anything not exercised end to end is untested, and exercise it.

**Not built:** care facility / practitioner / trainer / ambulance tab groups (Sheets 07–13, 18); bookings; chat; payouts (D12 on hold); the Business app Staff screen for P1-08d (the RPCs exist, the UI does not).
