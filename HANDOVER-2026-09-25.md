## 2. The one decision before you submit

`submit_medication_enquiry` was tightened this session (P1-01 bullets 2 and 3). **That tightening is live on prod now, while the old build is still in the stores.** Measured on prod, simulating the exact payloads an old build sends:

| Old (live) build submits | Result now |
|---|---|
| ordinary OTC drug, no `enquiry_category` key | **works** — the column defaults to `medicines` |
| a drug the backfill marked prescription-only (649 of 3,151) | **`rx_disabled`** → the old build shows its generic "Something went wrong" |
| an enquiry with a prescription photo | **`rx_disabled`** (before: accepted, then seen by nobody) |

So between now and the new build reaching users, someone on the current build enquiring about e.g. an antibiotic gets a generic error.

**Recommendation: ship as-is.** Refusing is the safe direction — before the change, a prescription-only drug submitted as `otc` was routed to `otc_medicines` vendors who could quote on it, which is the hole P1-01 bullet 3 exists to close. The new build handles it properly: it blocks the tap in the drug picker with "Prescription only — … please visit a pharmacy directly", and maps `rx_disabled` to real copy instead of the generic alert. The tightening and the build that explains it are meant to ship together, so ship promptly.

**If you cannot ship promptly** and want the old build to keep working meanwhile, the one-line softening is to blank the backfill (`update public.drugs set is_prescription_only = null where …`, see `20260924002000_*_ROLLBACK.sql`). That reopens the safety hole, so it is a deliberate trade, not a fix.

**Two pre-existing holes in chat RLS — fix these with step 4b, they touch the same policies**
1. **`messages` INSERT checks only `auth.uid() = sender_id`.** Any authenticated user can post into any conversation whose id they know. They cannot read it, but they can write to it.
2. **`conversation_members` INSERT is `auth.uid() = user_id`.** Anyone can add themselves to any conversation, and the SELECT policies then let them read every message in it. This is a read hole for every existing private thread.

Recommended (not applied, because both change shipped chat behaviour and want a smoke test with a real session): make `messages` INSERT require `is_conversation_member(conversation_id)`; replace the `conversation_members` INSERT policy with self-insert **only into an open group**, plus `user_can_manage_conversation(conversation_id)` for adding somebody else. Group creation is unaffected either way — it goes through the RPC on the service-role client, which bypasses RLS.
**⚠ If you attach `can_insert_conversation_member`, `user_can_manage_conversation` or `facility_has_privilege` to a policy, `grant execute … to authenticated` first.** An August 2026 audit revoked that grant and `CREATE OR REPLACE` preserves ACLs, so the policy would fail for real users. `is_conversation_member`, which is already used in live policies, has the grant.

## 6. The thing to expect from this database

**It is full of code that was written, never called, and therefore never found to be broken.** The previous handover said this; this session found nine more instances, every one by *calling* the thing rather than reading it:

| What | How it was broken |
|---|---|
| `reconcile_notification_receipts()` | waited for a pg_net response in the transaction that queued it — impossible; 1,492 consecutive failures, and **had never worked at all** |
| `fn_create_group_conversation` (both overloads) | passed `text` into `uuid` columns; group creation dead since 2026-07-27 |
| `can_insert_conversation_member` | `uuid = text`; also returned NULL not false; also still attached to nothing |
| `user_can_manage_conversation` | `uuid = text` |
| `facility_has_privilege` | `text = subscription_privilege` |
| `get_vendor_enquiry_inbox` | hardcoded its own copy of the capability map, so it could disagree with the alert; ignored capability `expires_at` |
| `drugs.atc_code` | NULL on all 3,151 rows, so half the planned backfill could not run |
| chat RLS | the two holes in §5 |
| `cron.job_run_details` "succeeded" | can mean "did nothing" — 4,452 green runs were runs with an empty batch |

Practical rules that follow:
- **Call it.** Reading a function, or seeing it in `database.types.ts`, proves nothing.
- **A green cron run is not a working cron job.** Check that it changed a row.
- **`cron.job_run_details` keeps the full PL/pgSQL CONTEXT stack** and is a far better diagnostic than `postgres_logs` for anything scheduled.
- **PostgREST kills any RPC at 8 s**: it connects as `authenticator`, whose `rolconfig` sets `statement_timeout = 8s`, and `SET ROLE service_role` does **not** lift it. Budget cold, not warm — cold is 3–4× worse on this instance.
- **After any `DROP FUNCTION` + `CREATE`, re-check `proacl`.** `CREATE FUNCTION` grants EXECUTE to PUBLIC by default.
- For JWT comparisons the working pattern is `user_id::text = public.request_user_id()`.

**Three things worth knowing about how it had to be done:**

1. **A provider's owner cannot be deleted.** `providers.owner_id` is `NOT NULL` but its FK is `ON DELETE SET NULL` — the two contradict, so deleting an owner fails with `23502` rather than orphaning the provider. **This is a latent bug**: the intended behaviour of that FK is unreachable. Worth deciding whether `owner_id` should become nullable or the FK should be `RESTRICT` and say so honestly. Until then, a provider must be reassigned or deleted before its owner can be.
